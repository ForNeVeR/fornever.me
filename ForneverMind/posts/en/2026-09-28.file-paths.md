    description: This post explains certain little-known details of how file paths work and relate to each other, in various systems (Windows, macOS, Linux).

A _file_ is one of the best known entities in computing; _opening a file_ is one of the most basic functions almost any programming language includes. A _file_ is, in most cases, a named location on a storage device that contains data. And a _file path_ is, thus, also a well known entity: it is some sort of textual identifier that can be used to access a _file_.

Almost everything in these basic definitions deserves an asterisk, because there are certain exceptions from each aspect: files are not necessarily named; the names are not necessarily textual; files aren't necessarily placed on a storage device; neither they have to contain data. But most programmers would think they agree on basic definitions, and in particular, how a _file path_ is supposed to act and look like.

In this post, we'll discuss some less-known details of file path behavior on various desktop operating systems (Linux, macOS, Windows).

## How Paths Looked Historically
First mentions of file path in hierarchical file system I was able to find come from MULTICS. For example, check the examples in [this document][multics.doc] describing a function that performs something similar to separation of a file and directory names from a full file path.

In MULTICS, a path consists of a sequence of names separated by characters `>` and `<`.

`>` means something like `/` on Unix (so, it's used as a root directory name, and also separates different names in a chain), while `<` is a reference to a parent directory, so you could say that it could be replaced by modern `/../`.

Later in computing, paths were changed to use the `/` and `\` separators we know today.

## Path Separators
Speaking of that. What separators do the modern operating systems use?

On Unix, it is really simple: `/` is the root folder designator and also a path separator. It separates different levels of the file system hierarchy, i.e. the directories in a path. `/foo/bar` means the `bar` file or directory inside the `foo` directory, which is inside the root directory.

On Windows, the situation is significantly more complex. The canonical path separator is `\`. E.g. `C:\Windows\System32` means the `System32` file or directory inside the `Windows` directory inside the root directory of the drive `C:`. However, Windows also supports `/` in _almost_ all the use cases, except some exotic paths (UNC and DOS device paths, `\\server\share`, `\\.\…`, and `\\?\…`).

Moreover, on certain locales (Imagine that? Locales are again cursed! What a surprise!), Windows will _render_ path separator as `¥` (on Japanese locale) or `₩` (on Korean locale). This is for the presentation only: the paths still use `\` character code underneath, but they get rendered as `¥` or `₩`. Read more in [Michael Kaplan's post][kaplan.backslash].

## Case Sensitivity
Let's start from a simple (he-he) question: are file paths supposed to be case-sensitive or not? If you only work with one operating system, your answer will probably be definite "yes" or definite "no". If you used to develop for multiple operating systems, you might answer more fully: on Linux (and BSD, for that matter), paths are case-sensitive (so, `Foo` and `foo` are different files), while on Windows (and macOS, which is a fact often surprising people, even if they use macOS themselves), paths are case-insensitive (so, `Foo` and `foo` are the same file).

There is, of course, a lot of complexity in how the systems define "case-insensitive" (and they _do_ define this differently), but we won't focus on this aspect in this post.

What we _will_ focus on, though, is the fact that this is not the whole truth. Linux doesn't have to be case-sensitive, and macOS/Windows don't have to be case-insensitive. All three systems provide general mechanisms to control and query case sensitivity of each path. On Windows, [you can control this][windows.fsutil] via `fsutil file setCaseSensitiveInfo`, and query it via `fsutil file queryCaseSensitiveInfo`. On Linux, you can mount both case-sensitive and case-insensitive file systems, and ext4, for example, supports this per-directory with the [**Casefold** attribute][linux.casefold]. On macOS, you can [control case sensitivity of each file system when creating them][macos.case-sensitive] (there's a flag on APFS that preserves the case sensitivity of the whole FS). You can mount a case-sensitive FS to your file system at any point.

This means that _generally speaking_, you cannot tell if a path is case-sensitive or not, only knowing the OS your code executes on. Every time you want to know this (and there are many reasons when you'd want to know this — e.g., when comparing the file paths to figure out if they point to the same file or directory), you need to query the file system (or, you know, employ other ways to compare the file identity).

## File Path Kinds
There are two well-known kinds of file paths: _absolute_ and _relative_.

An _absolute path_ is also known as a _fully qualified path_. It is a path that starts from the root directory of the file system. It is always unambiguous, and it does not depend on the current working directory: an absolute path to a file is always the same, regardless of where you are in the file system. An example of an absolute file path on Unix is `/usr/bin`. An example of an absolute file path on Windows is `C:\Windows`.

A _relative path_ is a path that is relative to the current working directory. Depending on your current working directory, it might point to different files or directories. An example of a relative file path is `./bin` (on both Windows and Unix, since Windows supports `/` separators in almost every file path).

Of course, there are some tricky questions regarding this matter. For example, consider the string `C:\Windows`. What is this, generally-speaking? What kind of path is it? Unfortunately, there's no answer: while it seems obvious this is an absolute Windows file path, _on Unix this is also a valid path_, and it is _relative_! It's actually a name of a file, that you can possibly create; nothing will prevent you from it.

## Path Combination
You can combine the basic paths, absolute and relative, to get a longer path, usually via the same path separator, `/` on Unix and `\` on Windows (though Windows mostly supports `/` as well). For example, a combination `C:\Windows` and `System32` will result in `C:\Windows\System32`. And a combination of `/usr` and `bin` will give you `/usr/bin`. Path combination is also a very simple operation. But as usual, there are some interesting details.

There are two special entries, `.` and `..`. `.` means the current directory (it's seldom used by itself, but you often see it e.g. in shell commands, to specify that you want to run an executable file from the current directory, and not a globally-available one). `..` means the parent directory of whatever directory you are currently working with. Both entries can be present in absolute or relative paths. For example, on Windows, `C:\Windows\..` is the same folder as `C:\`. The process of resolving `.` and `..` entries and removing duplicate path separators is called _path normalization_. It is a text-only process, it doesn't go on disk to check anything. These entries should be considered when combining paths.

There's one peculiar case of path combination: combination of _two absolute paths_. A user can combine paths `/usr` and `/bin`, and the result will be `/bin` — the last absolute path wins. [Nobody knows why it was implemented this way, and most parties refer to each other][lukas-prokop.path-behavior]. I was able to track the first glimpses of this behavior back to [Emacs code from 1985][emacs-1985]: see how the `expand-file-name` function seems to perform combination of paths. It seems like `(expand-file-name "/bar" "/foo")` would result in `/bar`, while `(exppand-file-name "bar" "/foo")` would result in `/foo/bar`. A more explicit mention you can see in [Python's `posixpath.py` from 1990][python-1990], in a function `cat` described to perform the "Intelligent pathname concatenation"

## Path Roots
(Yes, a plural!)

So, on Unix, there's only one root directory, and it's marked as `/`. Every other path relates to the root directory somehow. You always can build a _relative path_ between any two absolute paths.

On Windows, the situation is, as usual, significantly more complex. First, there are multiple _drives_, each one marked with a letter (e.g. `C:` or `D:`). Each drive has its own root directory, which is marked as `C:\` or `D:\`. Every other path on these drives relates to the root directory of the corresponding drive. `C:\` or `D:\` are called _the roots_. You cannot build a relative path between two absolute paths, if they belong to different drives.

If you consider exotic Windows paths, though, the situation become even more complex: on UNC paths, `\\server\share\` is considered the root of the share (so, it's always the server name plus the share name).

And for more exotic paths such as DOS devices (`\\?\` and `\\.\`) and object manager expressions (`\\??\`), there's an even more complex set of rules, and I was unable to even identify where this is documented.

On an absolute path, though, it's expected that taking its root is a valid operation, regardless of the definition the root directory takes for this particular path.

## Exotic Relative Paths
In all its wisdom, Windows introduces _two more_ kinds of non-absolute paths!

They have _drive-relative_ and _current directory on a drive_ paths:
- `C:Something` means `Something` file or folder inside of the current directory on drive `C:`. Other possible forms are e.g. `C:.\Something` or `C:..\Something`, all resolve relatively to the current directory on drive `C:` as well.

  What is the "current" directory on a drive? I am _so_ glad you asked! You see, Windows shell (mainly I think that's behavior of `cmd.exe` — I am not sure it's supported by any other shells or system APIs) remembers the _current directories_ on each drive separately. When you run `cd C:\Windows` in Cmd, it will act differently depending whether your current working directory is on drive `C:` or not. If you are already on this drive, it will just change the current working directory to whatever you asked. Otherwise, it will set the `C:` drive's working directory to `C:\Windows`, and not change the current working directory — meaning you'll stay on whatever other drive you were. If you want to change your active drive, you need to invoke the command `cd /d`.

  So, Windows' Cmd shell introduces the concept of per-drive working directory. And it keeps that in the special environment variables (e.g. `=C:` for `C:` drive) that are passed to each process you start from shell, and this allows the file system APIs to properly react when you request path relative to the current directory on a certain drive, such as `C:file.txt`.
- `\Something` is a _directory relative to a drive root_, without specifying what drive it is related to. So, when resolved, it will always take the current drive (i.e. the drive your current working directory is on) and use that as the base for this path.

Both these cases are, confusingly, something that .NET calls the "rooted paths" (`Path.IsPathRooted` returns `true` for both).

## Exotic Relative Path Resolve
These paths are resolved in very interesting ways, depending on the technology you use. And there are different opinions on what should happen when they are resolved.

Here,
- **Node.js** uses `path.join` (there's also an API `path.resolve`, but it always results in an absolute path, so it's harder to compare since it depends on the working directories across the affected drives; if I had to estimate, I's say it produces 8/8 "correct" answers as well, although absolute),
- **D** uses `std.path : buildPath`,
- **.NET** uses `System.IO.Path.Combine`,
- **Win32** uses `PathCombine` function,
- **Rust** uses `Path::join`,
- **Python** uses `path.join`,
- **Java** uses `java.lang.Path.resolve`,
- **C++17** uses `std::filesystem::path`,
- **TruePath** (a library we'll discuss below) uses `operator /` on `LocalPath`.

### What Do We Consider "Correct"
In the aforementioned table, I assigned "correctness" score according to the _mnemonic rule of resolve_ (not something normative, the one I invented), that explains how the path combination should work. **The path combination should result in the same path that you can come to via a sequence of calls of `cd` operation (or `cd /d`, for Cmd shell)**. For example (here I'll omit `/d` when not changing the drive):
- `"a" / "b"` is the same as `cd a && cd b`;
- `"C:\Windows" / "System32"` is the same as `cd /d C:\Windows && cd System32`;
- `"C:" / "Windows"` is the same as `cd /d C: && cd Windows`;
- `"C:x" / "C:y"` is the same as `cd /d C:x && cd y`, meaning — the same as `C:x\y`, same result we've got in several, but not all, of the technologies listed above.

This logic, to my surprise, is a well-defined [part of C++17 standard][cpp.standard].

Note that the C++ standard tries to describe the situation regarding the drives (aka "path roots") in generic terms: each path can declare `has_root_name() == true`, and rules about relative resolve then depend on whether paths' `root_name()` is the same or not.

## TruePath
You can see that .NET often gets the results "wrong". It doesn't have to! I have recently released a new version of [TruePath][truepath], a library that implements the "correct" behavior, according to _the mnemonic rule of file path resolve_. It also supports combining paths with `/` operator, allows you to strictly define a path as an `AbsolutePath` (so that no aforementioned shenanigans apply to your code), provides some file operations on paths (e.g. comparison with OS-default case sensitivity — and [it will handle the per-path sensitivity][truepath.case-sensitivity] one day as well!), and has other nice features.

## More Exotic Paths
This is not all! Windows has even more path kinds, the ones that are not yet correctly handled by TruePath (but will be handled in the future):
- **UNC Paths**, `\\server\share\path\to\file`;
- **Local Device Paths**, `\\.\C:\path\to\file`;
- **Root Local Device Paths**, `\\?\C:\path\to\file`.

Read [this wonderful document written by James Forshaw from Google Project Zero][google-project-zero.paths] on other interesting aspects of these paths.
