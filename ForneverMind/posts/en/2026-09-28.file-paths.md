    title: File Paths and Their Combinations
    description: This post explains certain little-known details of how file paths work and relate to each other, in various systems (Windows, macOS, Linux).
---

A _file_ is one of the best-known entities in computing; _opening a file_ is one of the most basic functions almost any programming language provides. A _file_ is, in most cases, a named location on a storage device that contains data. And a _file path_ is, thus, also a well-known entity: it is some sort of textual identifier that can be used to access a _file_.

Almost everything in these basic definitions deserves an asterisk, because there are certain exceptions to each aspect: files are not necessarily named; the names are not necessarily textual; files aren't necessarily placed on a storage device; nor do they have to contain data. But most programmers would think they agree on the basic definitions and, in particular, on how a _file path_ is supposed to act and what it is supposed to look like.

In this post, we'll discuss some lesser-known details of file path behavior on various desktop operating systems (Linux, macOS, Windows).

## How Paths Looked Historically
The first mentions of file paths in a hierarchical file system that I was able to find come from MULTICS. For example, check the examples in [this document][multics.doc] describing a function that performs something similar to separating the file and directory names from a full file path.

In MULTICS, a path consists of a sequence of names separated by the characters `>` and `<`.

`>` means something like `/` on Unix (so, it's used as the root directory name, and also separates different names in a chain), while `<` is a reference to a parent directory, so you could say that it could be replaced by the modern `/../`.

Later in computing, paths were changed to use the `/` and `\` separators we know today.

Some examples of MULTICS paths:
- `>a>b>c` means `/a/b/c`,
- `a>b<c` means `./a/b/../c`.

## Path Separators
Speaking of which: what separators do modern operating systems use?

On Unix, it is really simple: `/` is the root folder designator and also a path separator. It separates different levels of the file system hierarchy, i.e., the directories in a path. `/foo/bar` means the `bar` file or directory inside the `foo` directory, which is inside the root directory.

On Windows, the situation is significantly more complex. The canonical path separator is `\`. E.g., `C:\Windows\System32` means the `System32` file or directory inside the `Windows` directory inside the root directory of the drive `C:`. However, Windows also supports `/` in _almost_ all use cases, except for some exotic paths (UNC and DOS device paths, `\\server\share`, `\\.\…`, and `\\?\…`).

Moreover, in certain locales (Imagine that! Locales are cursed again! What a surprise!), Windows will _render_ the path separator as `¥` (in the Japanese locale) or `₩` (in the Korean locale). This is for presentation only: the paths still use the `\` character code underneath, but it gets rendered as `¥` or `₩`. So, if you copy a path on a Japanese or Korean version of Windows, you can paste it anywhere or send it to another user, and the path will bear the standard separators. Read more in [Michael Kaplan's post][kaplan.backslash].

## Case Sensitivity
Let's start with a simple (he-he) question: are file paths supposed to be case-sensitive or not? If you only work with one operating system, your answer will probably be a definite "yes" or a definite "no". If you have developed for multiple operating systems, you might answer more fully: on Linux (and BSD, for that matter), paths are case-sensitive (so, `Foo` and `foo` are different files), while on Windows (and macOS, a fact that often surprises people, even if they use macOS themselves), paths are case-insensitive (so, `Foo` and `foo` are the same file).

Of course, this is not the whole truth. Linux doesn't _have to_ be case-sensitive, and macOS/Windows don't _have_ to be case-insensitive. All three systems provide general mechanisms to control and query the case sensitivity of each path. On Windows, [you can control this][windows.fsutil] via `fsutil file setCaseSensitiveInfo`, and query it via `fsutil file queryCaseSensitiveInfo`. On Linux, you can mount both case-sensitive and case-insensitive file systems, and ext4, for example, supports this per-directory with the [**Casefold** attribute][linux.casefold]. On macOS, you can [control the case sensitivity of each file system when creating it][macos.case-sensitive] (there's a flag on APFS that preserves the case sensitivity of the whole FS). You can mount a case-sensitive FS to your file system at any point.

This means that _generally speaking_, you cannot tell whether a path is case-sensitive or not just by knowing the OS your code executes on. Every time you want to know this (and there are many situations when you'd want to know this — e.g., when comparing the file paths to figure out if they point to the same file or directory), you need to query the file system (or, you know, employ other ways to query the file identity).

But wait: **what is case-sensitive, anyway?** What does it mean? Well, of course, for different operating systems and file systems, this means different things!

Apple's HFS+ file system is [documented][hfs-plus.decomposition] to store file names in _fully decomposed form_, according to the table in the standard. Additionally, the standard provides the algorithm to perform the case-insensitive comparison of file names. So, case-insensitivity in the case of HFS+ comes from the very definition of the file system.

APFS (a newer file system from Apple), though, [doesn't force any form of normalization when storing the file names][apfs.implementation]: it stores all the names as-is. But macOS itself will still normalize the paths on APFS, similarly to how it's done for HFS+, [for compatibility (and sanity) reasons][apfs.normalization]! The case-insensitivity in this case acts according to the rules declared by the Unicode 9.0 format (I would assume they have updated this to newer Unicode standards later, but I was unable to find any documentation on this).

What about Microsoft? Are they doing anything similar? Of course — **nope**! While Microsoft file systems are also case-insensitive, they have a different set of quirks. The basic idea is that they don't normalize the file names in any way when saving them to disk, and they perform an ordinal-ignore-case comparison.

If you check the API for Windows drivers, you'll find the function [`FsRtlAreNamesEqual`][microsoft.are-names-equal] that generally compares the file names, and you will see a mysterious optional parameter `UpcaseTable`. What is an _"upcase table"_? Well, this is a table used to find the corresponding uppercase character (names are compared by converting them to uppercase, of all things!), and the table _is usually stored on disk_! So, for different versions of software to treat case equality on disk in the same way, file systems tend to store the whole Unicode table on disk in a special place, for all the software to refer to this table when necessary! You can read more interesting lore in [a post by Michael Kaplan][kaplan.case-insensitive]. See also: [the exFAT specification][exfat.upcase-table].

## File Path Kinds
There are two well-known kinds of file paths: _absolute_ and _relative_.

An _absolute path_ is also known as a _fully qualified path_. It is a path that starts from the root directory of the file system. It is always unambiguous, and it does not depend on the current working directory: an absolute path to a file is always the same, regardless of where you are in the file system. An example of an absolute file path on Unix is `/usr/bin`. An example of an absolute file path on Windows is `C:\Windows`.

A _relative path_ is a path that is relative to the current working directory. Depending on your current working directory, it might point to different files or directories. An example of a relative file path is `./bin` (on both Windows and Unix, since Windows supports `/` separators in almost every file path).

Of course, there are some tricky questions regarding this matter. For example, consider the string `C:\Windows`. What is this, generally speaking? What kind of path is it? Unfortunately, there's no answer: while it seems obvious that this is an absolute Windows file path, _on Unix this is also a valid path_, and it is _relative_! It's actually the name of a file that you can create; nothing will prevent you from doing so.

## Path Combination
You can combine the basic paths, absolute and relative, to (usually) get a longer path, using the path separator: `/` on Unix and `\` on Windows (though Windows mostly supports `/` as well). For example, a combination of `C:\Windows` and `System32` will result in `C:\Windows\System32`. And a combination of `/usr` and `bin` will give you `/usr/bin`. Path combination is also a very simple operation. But as usual, there are a lot of interesting details.

There are two special entries, `.` and `..`. `.` means the current directory (it's seldom used by itself, but you often see it, e.g., in shell commands, to specify that you want to run an executable file from the current directory, and not a globally available one). `..` means the parent directory of whatever directory you are currently working with. Both entries can be present in absolute or relative paths. For example, on Windows, `C:\Windows\..` is the same folder as `C:\`. The process of resolving `.` and `..` entries and removing duplicate path separators is called _path normalization_. It is a text-only process: it doesn't go to disk to check anything. These entries should be considered when combining paths.

There's one peculiar case of path combination: combining _two absolute paths_. A user can combine paths `/usr` and `/bin`, and the result will be `/bin` — the last absolute path wins. [Nobody knows why it was implemented this way, and most parties refer to each other][lukas-prokop.path-behavior]. I was able to track the first glimpses of this behavior back to [Emacs code from 1985][emacs-1985]: see how the `expand-file-name` function seems to perform a combination of paths. It seems like `(expand-file-name "/bar" "/foo")` would result in `/bar`, while `(expand-file-name "bar" "/foo")` would result in `/foo/bar`. A more explicit mention can be seen in [Python's `posixpath.py` from 1990][python-1990], in the function `cat`, described as performing "intelligent pathname concatenation".

## Path Roots
(Yes, plural!)

So, on Unix, there's only one root directory, and it's marked as `/`. Every other path relates to the root directory somehow. You can always build a _relative path_ between any two absolute paths.

On Windows, the situation is, as usual, significantly more complex. First, there are multiple _drives_, each one marked with a letter (e.g., `C:` or `D:`). Each drive has its own root directory, which is marked as `C:\` or `D:\`. Every other path on these drives relates to the root directory of the corresponding drive. `C:\` and `D:\` are called _the roots_. You cannot build a relative path between two absolute paths if they belong to different drives: there's no relative path between `C:\` and `D:\`.

If you consider exotic Windows paths, though, the situation becomes even more complex: for UNC paths, `\\server\share\` is considered the root of the share (so, it's always the server name plus the share name).

And for more exotic paths such as DOS devices (`\\?\` and `\\.\`) and object manager expressions (`\\??\`), there's an even more complex set of rules, and so far I have been unable to even identify where this is documented.

For any absolute path, it's expected that taking its root is a valid operation, regardless of the definition the root directory takes for this particular path.

## Exotic Relative Paths
In all its wisdom, Windows introduces _two more_ kinds of non-absolute paths!

These are _drive-relative_ and _current directory on a drive_ paths:
- `C:Something` means the `Something` file or folder inside the current directory on drive `C:`. Other possible forms are, e.g., `C:.\Something` or `C:..\Something`; all of them resolve relative to the current directory on drive `C:` as well.

  What is the "current" directory on a drive? I am _so_ glad you asked! You see, the Windows shell (I think that's mainly the behavior of `cmd.exe` — I am not sure it's supported by any other shells or system APIs) remembers the _current directories_ on each drive separately. When you run `cd C:\Windows` in Cmd, it will act differently depending on whether your current working directory is on drive `C:` or not. If you are already on this drive, it will just change the current working directory to whatever you asked. Otherwise, it will set the `C:` drive's working directory to `C:\Windows` and not change the current working directory — meaning you'll stay on whatever other drive you were on. If you want to change your active drive, you need to invoke the command `cd /d`.

  So, Windows' Cmd shell introduces the concept of a per-drive working directory. And it keeps these directories in special environment variables (e.g., `=C:` for the `C:` drive) that are passed to each process you start from the shell, and this allows the file system APIs to properly react when you request a path relative to the current directory on a certain drive, such as `C:file.txt`.
- `\Something` is a _directory relative to a drive root_, without specifying what drive it is related to. So, when resolved, it will always take the current drive (i.e., the drive your current working directory is on) and use that as the base for this path.

Both of these cases are, confusingly, what .NET calls "rooted paths" (`Path.IsPathRooted` returns `true` for both).

These paths are resolved in very interesting ways, depending on the technology you use. And there are different opinions on what should happen when they are resolved.

Here,
- **Node.js** uses `path.join` (there's also the `path.resolve` API, but it always results in an absolute path, so it's harder to compare since it depends on the working directories across the affected drives; if I had to estimate, I'd say it produces 8/8 "correct" answers as well, although they are absolute, and I decided not to include it in the comparison),
- **D** uses `std.path : buildPath`,
- **.NET** uses `System.IO.Path.Combine`,
- **Win32** uses the `PathCombine` function,
- **Rust** uses `Path::join`,
- **Python** uses `path.join`,
- **Java** uses `java.lang.Path.resolve`,
- **C++17** uses `std::filesystem::path`,
- **TruePath** (a library we'll discuss below) uses `operator /` on `LocalPath`.

While preparing this report, I found that .NET changed its behavior regarding certain paths around .NET Core 2.1, and they forgot to document this, so I opened [an issue][dotnet-issue], and [my PR][dotnet-pr] fixing the documentation on the `Path` API in .NET has been merged.

### What Do We Consider "Correct"?
In the aforementioned table, I assigned the "correctness" score according to the _mnemonic rule of resolve_ (not something normative, just one I invented), which explains how path combination should work. **Path combination should result in the same path that you can arrive at via a sequence of `cd` calls (or `cd /d`, for the Cmd shell)**. For example (here I'll omit `/d` when not changing the drive):
- `"a" / "b"` is the same as `cd a && cd b`;
- `"C:\Windows" / "System32"` is the same as `cd /d C:\Windows && cd System32`;
- `"C:" / "Windows"` is the same as `cd /d C: && cd Windows`;
- `"C:x" / "C:y"` is the same as `cd /d C:x && cd y`, meaning the same as `C:x\y` — the same result we got in several, but not all, of the technologies listed above.

This logic, to my surprise, is a well-defined [part of the C++17 standard][cpp.standard].

Note that the C++ standard tries to describe the situation regarding the drives (aka "path roots") in generic terms: each path can declare `has_root_name() == true`, and the rules of relative resolution then depend on whether the paths' `root_name()` values are the same or not. My understanding is that this terminology covers the logic regarding Windows network shares and various exotic paths as well, but I haven't checked that yet.

## TruePath
You can see that .NET often gets the results "wrong". It doesn't have to! I have recently released a new version of [TruePath][truepath], a .NET library that implements the "correct" behavior, according to _the mnemonic rule of file path resolve_. It also supports combining paths with the `/` operator, allows you to strictly define a path as an `AbsolutePath` (so that none of the aforementioned shenanigans apply to your code), provides some file operations on paths (e.g., comparison with OS-default case sensitivity — and [it will (optionally) handle the per-path sensitivity][truepath.case-sensitivity] one day as well!), and has other nice features.

## More Exotic Paths
That's not all! Windows has even more path kinds, ones that are not yet correctly handled by TruePath (but will be handled in the future):
- **UNC Paths**, `\\server\share\path\to\file`;
- **Local Device Paths**, `\\.\C:\path\to\file`;
- **Root Local Device Paths**, `\\?\C:\path\to\file`.

Read [this wonderful document written by James Forshaw from Google Project Zero][google-project-zero.paths] on other interesting aspects of these paths.
