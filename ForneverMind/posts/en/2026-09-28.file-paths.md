A _file_ is one of the best known entities in computing; _opening a file_ is one of the most basic functions almost any programming language includes. A _file_ is, in most cases, a named location on a storage device that contains data. And a _file path_ is, thus, also a well known entity: it is some sort of textual identifier that can be used to access a _file_.

Almost everything in these basic definitions deserves an asterisk, because there are certain exceptions from each aspect: files are not necessarily named; the names are not necessarily textual; files aren't necessarily placed on a storage device; neither they have to contain data. But most programmers would think they agree on basic definitions, and in particular, how a _file path_ is supposed to act and look like.

In this post, we'll discuss some less-known details of file path behavior on various desktop operating systems (Linux, macOS, Windows).

## Case Sensitivity
Let's start from a simple (he-he) question: are file paths supposed to be case-sensitive or not? If you only work with one operating system, your answer will probably be definite "yes" or definite "no". If you used to develop for multiple operating systems, you might answer more fully: on Linux (and BSD, for that matter), paths are case-sensitive (so, `Foo` and `foo` are different files), while on Windows (and macOS, which is a fact often surprising people, even if they use macOS themselves), paths are case-insensitive (so, `Foo` and `foo` are the same file).

There is, of course, a lot of complexity in how the systems define "case-insensitive" (and they _do_ define this differently), but we won't focus on this aspect in this post.

What we _will_ focus on, though, is the fact that this is not the whole truth. Linux doesn't have to be case-sensitive, and macOS/Windows don't have to be case-insensitive. All three systems provide general mechanisms to control and query case sensitivity of each path. On Windows, [you can control this][windows.fsutil] via `fsutil file setCaseSensitiveInfo`, and query it via `fsutil file queryCaseSensitiveInfo`. On Linux, you can mount both case-sensitive and case-insensitive file systems, and ext4, for example, supports this per-directory with the [**Casefold** attribute][linux.casefold]. On macOS, you can [control case sensitivity of each file system when creating them][macos.case-sensitive] (there's a flag on APFS that preserves the case sensitivity of the whole FS). You can mount a case-sensitive FS to your file system at any point.

This means that _generally speaking_, you cannot tell if a path is case-sensitive or not, only knowing the OS your code executes on. Every time you want to know this (and there are many reasons when you'd want to know this — e.g., when comparing the file paths to figure out if they point to the same file or directory), you need to query the file system (or, you know, employ other ways to compare the file identity).

## File Path Kinds
There are two well-known kinds of file paths: _absolute_ and _relative_.

An _absolute path_ is also known as a _fully qualified path_. It is a path that starts from the root directory of the file system. It is always unambiguous, and it does not depend on the current working directory: an absolute path to a file is always the same, regardless of where you are in the file system. An example of an absolute file path on Unix is `/usr/bin`. An example of an absolute file path on Windows is `C:\Windows`.

A _relative path_ is a path that is relative to the current working directory. Depending on your current working directory, it might point to different files or directories. An example of a relative file path is `./bin` (on both Windows and Unix, since Windows supports `/` separators in almost every file path).

Of course, there are some tricky questions regarding this matter. For example, consider the string `C:\Windows`. What is this, generally-speaking? What kind of path is it? Unfortunately, there's no answer: while it seems obvious this is an absolute Windows file path, _on Unix this is also a valid path_, and it is _relative_! It's actually a name of a file, that you can possibly create; nothing will prevent you from it.

## Path Combination
You can combine the basic paths, absolute and relative, to get a longer path, usually via the same path separator, `/` on Unix and `\` on Windows (though Windows mostly supports `/` as well). For example, a combination `C:\Windows` and `System32` will result in `C:\Windows\System32`. And a combination of `/usr` and `bin` will give you `/usr/bin`.
